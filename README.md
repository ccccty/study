## 进度是怎么存的

这是本项目最需要说清楚的一点——「我到底学过这张卡没有」不能丢。

记忆状态（每张卡的复习次数、间隔天数、下次到期日）分三层落盘：

| 层 | 作用 | 什么时候用 |
|---|---|---|
| `localStorage` | 主存储，同步读写 | 首屏渲染，不等异步 |
| `IndexedDB` | 镜像备份，写入串行化 | 启动时与 localStorage 比对，取较新的那份 |
| `navigator.storage.persist()` | 申请持久化 | 降低系统清理存储的概率 |

- 清缓存、无痕模式导致 `localStorage` 被抹掉时，刷新后会自动从 `IndexedDB` 恢复。
- 两者都被清（比如换手机、卸载浏览器），就只能靠「数据」页的导出文件恢复。
- **进度只存在本机浏览器内，不上传任何服务器。** 换设备请用导出 / 导入。

> 实现上有一个坑：连续快速评分时，如果每次 `save()` 都新开一个 IndexedDB 事务，完成顺序不保证，最后落盘的可能是较早的快照（实测只剩 1 张卡）。所以 `idbSet` 用单例连接 + Promise 串行队列，严格保证最后一次写入最后落盘。

## 卡片结构

八字段，缺任何一个都不算合格卡片：

| 字段 | 含义 |
|---|---|
| `cat` | 分类键，取值见 `index.html` 的 `CATS` |
| `term` | 术语，不带括号注释 |
| `en` | 英文名 |
| `one` | 一句话定义，只回答「是什么」 |
| `jd` | **岗位场景**，为什么考它——这是本项目的核心字段 |
| `pts` | 原理要点 3–4 条，至少一条带数值、公式或量级 |
| `use` | 工程上怎么用 |
| `trap` | 容易踩的坑，必须具体可验证 |

内置卡写在 `index.html` 的 `RAW` 数组里；每日新增走 `cards.json`，由外部流水线写入。

两类卡的 id 规则不同，都做了稳定性处理：

- 内置卡 `c0…cN`：只允许在末尾追加，不能插入或重排
- 增量卡 `x<hash>`：按术语哈希生成，`cards.json` 里顺序变化不会让已有进度错位

## 每日更新

页面每次打开都会带时间戳拉一次 `cards.json`（`?t=…` + `no-store`），所以只要数据变了，打开就是新的，**日常不需要手动操作**。

只有 `index.html` 本身更新（界面或内置卡）时，才需要点「数据」页的「刷新题库」强制重载，绕开 GitHub Pages 的 10 分钟 CDN 缓存。

`git push` 后 Pages 自动重建，通常 1–2 分钟生效。

## 相关的本地流水线

抓取与写卡逻辑不在本仓库，在本地 `pipeline/`：

- `config.json`：目标城市、岗位方向、检索关键词
- `merge_cards.py`：把 `candidates/*.json` 合并进本仓库的 `cards.json`（幂等，按术语去重）
- `jd_to_cards.md`：八字段写卡规范，含 `jd` 的正反例
