# 岗位 JD → 概念卡片 生成规范

这个文件是「抽词 + 写卡」那一步的唯一标准。自动化任务每天按它执行；你自己补卡也照它写，`merge_cards.py` 会按同样的规则校验。

**核心原则：卡片不是百科条目，是「岗位为什么需要它」+「它到底是什么」。** 一张卡的顺序永远是——先讲岗位场景，再讲定义，最后讲坑。学的人是在准备面试，不是在编教材。

---

## 一、什么词才配做成卡片

三道闸门，全部通过才生成：

**1. 频次闸门**：同一概念被 **≥ 3 个不同岗位** 的 JD 提到（阈值在 `config.json` 的 `minMentions`）。只出现一次的多半是某家公司的内部叫法。

**2. 概念闸门**：必须是**有定义、有原理、有工程含义**的名词。

| 收 | 不收 |
|---|---|
| 技术概念：TF2、ros2_control、Kalman 滤波、时间同步、ASIL | 泛能力描述：沟通能力强、抗压、owner 意识 |
| 工具与标准：Nav2、AUTOSAR、ISO 26262、CANoe | 纯工具名：Office、Visio（没有原理可讲） |
| 方法与流程：FMEA、标定、数据闭环、Sim2Real | 公司/项目名、产品型号 |
| 指标与量纲：Cpk、mAP、回环误差、TOPS | 学历、年限、语言要求 |

**3. 缺口闸门**：归一化后不在现有题库里。归一化会去空白、去括号注释、转小写，所以「IMU（惯性测量单元）」和「IMU」算同一个。

## 二、每张卡的八个字段

```json
{
  "cat": "ros2",
  "term": "TF2 坐标变换树",
  "en": "TF2 Transform Tree",
  "one": "ROS 2 里管理所有坐标系之间变换关系的时间缓冲树，任意两个 frame 都能查到某一时刻的相对位姿。",
  "jd": "岗位高频表述：熟悉 TF 坐标变换，能独立完成多传感器外参标定与坐标对齐。面试会追问 map 和 odom 为什么要拆成两层。",
  "pts": [
    "结构是树，每个 frame 只能有一个父节点；标准链是 map 到 odom 到 base_link 到各传感器",
    "查询必须带时间戳，TF2 会做时间插值；超出缓冲（默认 10 秒）就报 extrapolation 错误",
    "固定外参用 static_transform_publisher 发布，动态变换由里程计与定位节点发布"
  ],
  "use": "把不同传感器数据统一到同一坐标系、机械臂末端位姿求解、多机协同定位。",
  "trap": "把外参硬编码在代码里、TF 树里又配一份不一致的值，是最难查的一类 bug。"
}
```

| 字段 | 要求 | 长度 |
|---|---|---|
| `cat` | `sens` `radar` `fusion` `est` `mcu` `bus` `deploy` `auto` `ml` `embodied` `quant` `ros2` 之一 | — |
| `term` | 中文主名称，不带括号注释 | ≤40 字 |
| `en` | 英文名或通用缩写，没有就留空 | ≤80 字 |
| `one` | **一句话定义**，只回答「是什么」 | 8–120 字 |
| `jd` | **岗位场景**，回答「为什么考它」——见下节 | 8–220 字 |
| `pts` | **原理与要点 3–4 条**，每条一个可独立考的知识点 | 每条 ≤160 字 |
| `use` | 工程上具体用在哪，对得上真实模块或场景 | 8–160 字 |
| `trap` | **最容易踩的坑**，具体、可验证 | 8–160 字 |

## 三、`jd` 字段怎么写（这是最容易被写废的字段）

它要回答的是：**这个知识点会在什么类型的岗位、什么工作环节里被用到，面试会怎么问。**

三种合格写法，从好到次：

**1. 岗位表述 + 追问点**（最好）
> 岗位高频表述：熟悉 TF 坐标变换，能独立完成多传感器外参标定与坐标对齐。面试会追问 map 和 odom 为什么要拆成两层。

**2. 工作环节还原**
> 多传感器融合项目里，标定完的外参要落到 TF 树才能被全链路复用；改完 extrin.json 忘了改 launch 文件是最常见的翻车点。

**3. 职责原话概括**
> 岗位职责原话：搭建仿真测试环境与回归用例——ROS 2 项目里这基本等于 use_sim_time 与 rosbag 回放。

**明确不许写的：**

- ✗ `该岗位要求掌握本概念` —— 等于没写
- ✗ `这是机器人领域的重要概念` —— 空话
- ✗ 编造公司名和薪资 `某头部公司 40k 岗位要求…` —— 假信息比没有更糟
- ✗ 大段抄 JD 原文 —— 卡片要的是提炼，不是复印

**长度控制在 2 句以内。** 第一句说场景，第二句说面试会追到哪一层。

## 四、质量红线

- **`pts` 里至少一条要带可量化的东西**：数量级、公式、典型参数、阈值、对比关系。
  - ✗ `CAN FD 速度很快，适合大数据量传输`
  - ✓ `数据段可变速率（最高 5–8Mbps），仲裁段仍用低速保证兼容，单帧最长 64 字节`
- **`trap` 不许写正确的废话**。`注意安全`、`需要多实践`、`参数要调好` 一律不合格。合格的坑长这样：
  - `在定时器中断里喂狗等于没装看门狗：主循环卡死了但中断还在跑，设备永远不复位。`
- **不要抄 JD 话术**。JD 写「精通 Kalman 滤波」，卡片要写的是五步流程和 Q/R 的物理含义。
- **不确定就不写**。宁可今天只加 2 张，也不要把「据我理解」写进题库——卡片是要背进脑子的，错的概念比没有更贵。

## 五、抽取时信息量最高的位置

JD 里的概念密度并不均匀：

1. **「岗位职责」第 2–4 条**：通常写具体做什么模块，是 `use` 字段的素材
2. **「任职要求」的技术栈罗列**：协议、工具链、标准号、算法名，是 `term` 的主要来源
3. **加分项**：往往揭示团队真实方向（`有 Sim2Real 经验优先`）
4. **中英混排缩写**：`VLA` `BEV` `HIL` `SIL` `TF2` `PPAP`
5. **带数字的要求**：`10ms 以内`、`99.9% 可用性`、`ASIL-D`——数字背后就是一个概念
6. **多份 JD 的重复表述**：完全相同的措辞说明这是行业通用要求，`jd` 字段可以直接提炼

## 六、输出格式

存到 `pipeline/candidates/YYYY-MM-DD.json`：

```json
{
  "date": "2026-10-27",
  "cities": ["上海", "南京", "成都", "苏州"],
  "jdCount": 128,
  "source": "boss-scrape",
  "cards": [ /* 上面的八字段对象 */ ]
}
```

然后合并：

```bash
python pipeline/merge_cards.py pipeline/candidates/2026-10-27.json --max 8
```

先加 `--dry-run` 看会加什么、会跳过什么，确认没问题再去掉。

**注意**：`jd` 是必填字段。缺 `jd` 的卡片会被 `merge_cards.py` 直接拒绝——因为「没有岗位场景的卡片」不符合这个题库的定位。
